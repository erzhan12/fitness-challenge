     1|# Feature 0006: Numbers-only Multi-Challenge Mapping
     2|
     3|## Description
     4|
     5|When the user enters **two or more numbers** (examples: `5, 2`, `5 2`, `(5 2)`), the app should interpret the message as **counts for active challenges**, in a deterministic order:
     6|
     7|- The **first number** maps to the “default challenge”:
     8|  - If any active challenge has `is_default=True`, choose the one with the **lowest** `exercise_challenges.id` (deterministic tie-break).
     9|  - If none are default, choose the challenge with the **lowest** `exercise_challenges.id`.
    10|- The **second and subsequent numbers** map to the remaining active challenges in **increasing** `exercise_challenges.id` order (excluding the chosen default).
    11|- If the user provides **more numbers than active challenges**, extra numbers are **ignored**.
    12|
    13|This behavior must apply to **both**:
    14|- Telegram logging flow (`app/services/workout_service.py`)
    15|- REST parsing endpoint (`POST /api/v1/workouts/parse` in `src/api/routers/workouts.py`)
    16|
    17|Notes:
    18|- This feature only applies to **numbers-only** inputs (numbers + separators). Any message containing exercise words should keep using existing deterministic parsing / LLM parsing behavior.
    19|- Count validation rules stay the same (positive integers only; decimals/zero/negative should be rejected with the existing error message).
    20|
    21|## Relevant Existing Behavior
    22|
    23|- Default challenge selection exists in `determine_default_exercise` (`app/services/workout_service.py`) and uses:
    24|  - single active challenge → that challenge’s exercise type
    25|  - multiple active challenges → `is_default=True` (lowest id wins ties)
    26|  - otherwise → fallback `pushups`
    27|- Deterministic parsing in `app/services/deterministic_parser.py` currently does **not** support “two numbers only” (it returns `None` unless the input is a single number with exactly one exercise type in scope). This makes the new behavior a safe, explicit special-case.
    28|
    29|## Files / Functions to Modify
    30|
    31|### 1) Telegram flow: `app/services/workout_service.py`
    32|
    33|- **Function**: `process_incoming_message(text: str, chat_id: int)`
    34|  - Add a **numbers-only multi-number detection** step before calling `parse_workout_message(...)`.
    35|  - When detected and when there are active challenges, map the numbers to challenges and build parsed entries without calling the LLM.
    36|  - Ensure per-entry processing uses the mapped challenge (not just `challenge_map` by exercise type) so each number is attributed to the intended challenge.
    37|
    38|- **Function**: `determine_default_exercise(challenges_data, exercise_types)`
    39|  - Keep as-is for “single number without exercise” behavior.
    40|  - For this feature, we need a similar rule but returning a **default challenge id** rather than an exercise name; implement as a small helper (see “Implementation Outline”).
    41|
    42|### 2) REST parsing endpoint: `src/api/routers/workouts.py`
    43|
    44|- **Endpoint**: `POST /workouts/parse`
    45|  - Today the endpoint calls `parse_workout_message(data.text, exercise_types)` without a dynamic default and without challenge ordering context.
    46|  - Update it to:
    47|    - Fetch the same “current active challenges” used by Telegram (date-windowed active challenges).
    48|    - Apply the same numbers-only multi-number mapping logic as Telegram.
    49|    - Otherwise (non-numbers-only), keep the existing behavior (deterministic + LLM), but pass an appropriate `default_exercise_name` consistent with Telegram when possible.
    50|
    51|### 3) Shared DB query helper: `src/api/services.py` (or a new shared helper module)
    52|

    55|- **New function (suggested)**: `list_current_active_challenges(target_date: Optional[date] = None) -> List[Dict[str, Any]]`
    56|  - Filters:
    57|    - `is_active=True`
    58|    - `start_date <= target_date <= end_date` (same as Telegram)
    59|  - Returns raw dict rows including `id`, `exercise_type_id`, `is_default`, `start_date`, `end_date`.

    78|## Algorithm (Step-by-Step)
    79|
    80|### A) Detect “numbers-only multi-number” input
    81|
    82|Given `text`:
    83|1. Normalize by trimming whitespace.
    84|2. Allow only separators like whitespace, commas, parentheses/brackets; treat them as token boundaries.
    85|3. Extract integer tokens in order.
    86|4. The fast-path is eligible when:
    87|   - There are **2+ integer tokens**
    88|   - The remaining characters (after removing integers and allowed separators) contain **no letters**
    89|   - All counts are valid positive integers (> 0)
    90|5. If any decimal-like pattern is present (e.g. `0.5`), return an invalid `ParseResult` with:
    91|   - `"Count must be greater than 0 and should be an integer."`
    92|
    93|### B) Determine ordered challenges list
    94|
    95|Inputs: `challenges_data` (current active challenges), and each challenge has at least `id`, `exercise_type_id`, `is_default`.
    96|
    97|1. If there are **no active challenges**, do not use this feature (fall back to existing parsing).
    98|2. Pick `default_challenge`:
    99|   - If any challenge has `is_default=True`, choose the one with the lowest `id`.
   100|   - Else choose the challenge with the lowest `id`.
   101|3. Build `ordered_challenges`:
   102|   - First element = `default_challenge`
   103|   - Remaining elements = all other challenges sorted by increasing `id`
   104|
   105|### C) Map numbers → challenges and create entries
   106|
   107|Inputs: `counts` (list[int]) and `ordered_challenges`.
   108|
   109|1. Pair counts with challenges by index:
   110|   - For i in `[0 .. min(len(counts), len(ordered_challenges)) - 1]`
   111|     - count = `counts[i]`
   112|     - challenge = `ordered_challenges[i]`
   113|2. For each pair:
   114|   - Look up the exercise type for `challenge.exercise_type_id` from the current `exercise_types`.
   115|   - Create an entry `{exercise_type_name, count, duration_seconds, notes=None, confidence=1.0}`.
   116|     - For time-based exercises: set `duration_seconds = count * 60` when the unit represents minutes (`minute` / `minutes` / `min`).
   117|3. Any counts that cannot be mapped (missing exercise type) should be skipped; if all are skipped, fall back to existing parsing.
   118|
   119|### D) Telegram persistence behavior
   120|
   121|In Telegram `process_incoming_message`:
   122|1. Use the mapped challenge (by id) when computing stats / inserting logs, so each number attaches to the intended challenge.
   123|2. Keep the rest of the logging pipeline unchanged (stats computation, response formatting, etc.).
   124|
   125|## Implementation Outline (No Code)
   126|
   127|1. Add a small parsing helper (location TBD) that:
   128|   - Detects numbers-only multi-number input
   129|   - Returns an ordered list of counts or an invalid result
   130|2. Add a small helper that:
   131|   - Builds `ordered_challenges` according to the rules above
   132|3. Integrate into:
   133|   - `app/services/workout_service.py::process_incoming_message` (Telegram)
   134|   - `src/api/routers/workouts.py::parse_workout` (REST)
   135|4. Add service-layer helper(s) in `src/api/services.py` for “current active challenges” so REST and Telegram share the same definition.
   136|5. Add unit + API tests as outlined above.
