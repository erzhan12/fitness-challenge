# Feature Plan: REST API Endpoints and OpenAPI Documentation

## Description

Introduce a **full internal REST API** that exposes all core fitness challenge operations (exercises, challenges, logs, and stats) over HTTP, with **OpenAPI/Swagger documentation**.  
The API will be **internal-only** (secured by an API key and not exposed to the public internet by default), but designed so it can later be safely consumed by external clients such as mobile or web apps.

## Current Architecture Overview

- **`app/main.py`**
  - Creates a FastAPI application titled `"Fitness Challenge Bot"`.
  - Includes `telegram` and `admin` routers.
  - Exposes a root health check endpoint at `GET /` returning a simple JSON payload.
- **`app/routers/telegram.py`**
  - Exposes `POST /telegram/webhook` to receive Telegram updates.
  - Verifies the Telegram secret header and enqueues processing of incoming messages via `process_incoming_message`.
- **`app/routers/admin.py`**
  - Exposes `POST /jobs/daily-reminder` secured by `ADMIN_API_KEY`.
  - Triggers `check_daily_reminders` (cron-style internal job).
- **`app/models.py`**
  - Defines Pydantic models for:
    - Parsing layer: `ExerciseEntry`, `ParseResult`.
    - Telegram objects: `TelegramUser`, `TelegramChat`, `TelegramMessage`, `TelegramUpdate`.
    - Domain/data objects: `ExerciseType`, `ExerciseChallenge`, `UserStats`.
- **`app/services/workout_service.py`**
  - Encapsulates Supabase-backed domain logic for:
    - Loading exercise types and active challenges.
    - Computing progress, status, and catch-up reps.
    - Inserting and deleting exercise logs.
    - Maintaining `user_stats` aggregates.
    - Processing Telegram commands (`/start`, `/undo`, `/recent`, `/delete`).
  - Currently returns **HTML-formatted Telegram messages** rather than JSON payloads.
- **`app/services/openai_service.py`**
  - Uses the configured LLM provider to:
    - Parse free-form workout text into `ParseResult`.
    - Generate motivational comments based on stats.
- **`app/services/telegram_client.py`**
  - Sends outgoing messages to Telegram via HTTP.
- **`app/dependencies.py`**
  - Initializes a shared Supabase client and exposes `get_supabase()`.
- **Supabase tables (inferred from queries)**
  - `exercise_types`, `exercise_challenges`, `exercise_logs`, `user_stats`.

The current HTTP surface is optimized for Telegram webhooks and a single admin job endpoint, with no general-purpose JSON REST API for direct programmatic access.

## High-Level Design

- **New internal API layer**
  - Create a new package under `src/api/` that defines:
    - HTTP routers for REST endpoints.
    - API-facing request/response schemas.
    - Thin service functions that orchestrate calls to Supabase and existing domain helpers.
  - This layer will be **HTTP and JSON-first**, returning structured JSON objects rather than HTML-formatted strings.
- **Base path and versioning**
  - Introduce a dedicated API prefix such as `/api/v1` for all new REST endpoints.
  - Keep existing Telegram and admin routes (`/telegram`, `/jobs`) as-is for backward compatibility.
- **Internal-only access**
  - Use an API key mechanism (based on `ADMIN_API_KEY` or a new dedicated `INTERNAL_API_KEY`) required on all state-changing endpoints, and optionally on read-only endpoints.
  - Assume the API is deployed behind a private network, VPN, or gateway; the plan does not expose it to the public internet by default.
- **Reuse existing domain logic**
  - Extract and reuse logic from `workout_service` for:
    - Computing exercise stats over challenges and days.
    - Inserting and deleting logs.
    - Maintaining `user_stats`.
  - Avoid duplicating business rules; instead, share computations between Telegram flows and the REST API.
- **OpenAPI/Swagger documentation**
  - Rely on FastAPI’s automatic OpenAPI generation while:
    - Defining clear Pydantic models for all request and response bodies.
    - Grouping endpoints under meaningful tags (e.g., `Exercises`, `Challenges`, `Logs`, `Stats`, `Jobs`).
    - Adding summaries, descriptions, and example payloads to improve generated documentation.

## Data and Models

### Domain entities

- **ExerciseType**
  - Fields (inferred): `id`, `name`, `display_name`, `emoji`, `unit`, `aliases`, `is_active`.
  - Represents different types of exercises (e.g., pushups, squats).
- **ExerciseChallenge**
  - Fields (inferred): `id`, `exercise_type_id`, `start_date`, `end_date`, `target_total`, `daily_target`, `challenge_name`, `is_active`.
  - Represents a time-bounded challenge and target totals for one exercise type.
- **ExerciseLog**
  - Fields (inferred from usage): `id`, `exercise_type_id`, `challenge_id`, `date`, `timestamp`, `count`, `cumulative_total`, `day_number`, `status`, `raw_message`, `duration_seconds`, `notes`.
  - Represents a single log entry of a user’s workout.
- **UserStats**
  - Fields (inferred): `exercise_type_id`, `all_time_total`, `best_daily_count`, `current_streak`, `longest_streak`, `last_logged_date`.
  - Represents pre-computed statistics over logs for performance and quick lookup.

### API-facing models (new)

- **Location**: `src/api/models.py`.
- **Read models**
  - `ExerciseTypeOut`: JSON representation of an exercise type, aligned with `ExerciseType`.
  - `ExerciseChallengeOut`: JSON representation of a challenge, including computed fields such as `total_days` and whether it is currently active.
  - `ExerciseLogOut`: JSON representation of a log entry that hides internal-only fields if necessary and normalizes timestamps and dates.
  - `ExerciseStatsOut`: Summary stats for an exercise, including fields such as `day_number`, `total_days`, `target_total`, `daily_target`, `today_total`, `cumulative_total`, `status`, `catch_up_reps`, and derived progress percentage.
  - `UserStatsOut`: Representation of user-level aggregates per exercise type.
- **Write models**
  - `ExerciseTypeCreate` and `ExerciseTypeUpdate`: For managing exercise types via the API.
  - `ExerciseChallengeCreate` and `ExerciseChallengeUpdate`: For creating and modifying challenges.
  - `ExerciseLogCreate`: For posting new logs with fields such as `exercise_type_id`, `count`, `date` (optional; default today), `duration_seconds` (optional), `notes` (optional), and optional `raw_message`.
  - Optionally, `ParseWorkoutRequest` and `ParseWorkoutResponse` if a parsing endpoint is exposed.

These API models should be explicitly separated from Telegram-specific models and HTML formatting so they remain stable for future mobile/web clients.

## Service Layer and Refactoring

### New API service module

- **Location**: `src/api/services.py` (or a small set of modules under `src/api/services/`).
- **Responsibilities**
  - Provide functions that implement core operations in a way that is:
    - Independent of Telegram message formatting.
    - Reusable both by REST endpoints and any future integration points.
  - Use `get_supabase()` from `app.dependencies` for database interactions.

### Refactor shared computations

- **Exercise stats computation**
  - Extract the numerical/statistical logic currently embedded in `get_exercise_stats_and_message` into a new helper (for example, a function that returns just the stats dict without formatting an HTML message).
  - The helper should:
    - Accept parameters such as `sb`, `exercise_type`, `challenge`, `today_local`, and `added_count`.
    - Query `exercise_logs` to compute cumulative totals and today’s totals.
    - Determine `day_number`, `total_days`, and `target_total` based on `ExerciseChallenge`.
    - Call `calculate_status_and_deficit` to get status and deficit and derive `catch_up_reps`.
    - Return a structured stats object (matching `ExerciseStatsOut`).
  - Update `get_exercise_stats_and_message` to call this helper, then build the HTML message from the returned stats, keeping Telegram behavior unchanged.

- **Log insertion and stats update**
  - Extract the logic that:
    - Inserts into `exercise_logs`.
    - Updates or inserts into `user_stats`.
  - Wrap it in an API-friendly function that accepts a `ExerciseLogCreate`-style input and returns:
    - The created log record.
    - The updated stats for the corresponding exercise type.

- **Log deletion**
  - Wrap the existing `delete_log_entry` logic into a reusable operation that:
    - Deletes a given log.
    - Updates `user_stats`.
    - Returns a structured result that the API can surface (without HTML formatting).
  - Keep the Telegram-facing HTML response path for `/delete` intact by formatting around this shared operation.

This refactoring ensures the REST API uses the same business rules as the Telegram bot while returning JSON instead of HTML.

## REST API Endpoints

All endpoints below are assumed to be mounted under a base prefix such as `/api/v1`.  
Existing routes under `/telegram` and `/jobs` remain as-is.

### Exercises

- **List exercises**
  - **Method/Path**: `GET /exercises`
  - **Behavior**:
    - Returns all exercise types, optionally filtered via query parameters:
      - `is_active` (default true).
      - Optional `challenge_only` that restricts to exercise types with at least one active challenge.
    - Uses Supabase to query `exercise_types` and, if `challenge_only` is true, joins or filters based on `exercise_challenges`.
  - **Response**:
    - List of `ExerciseTypeOut` objects.

- **Get exercise by ID**
  - **Method/Path**: `GET /exercises/{exercise_type_id}`
  - **Behavior**:
    - Fetches a single exercise type by ID.
    - Returns `404` if not found.

- **Create exercise type (optional for now)**
  - **Method/Path**: `POST /exercises`
  - **Behavior**:
    - Accepts `ExerciseTypeCreate`.
    - Inserts a new record into `exercise_types`.
  - **Considerations**:
    - Initially, may be restricted to internal admin tools; later, a UI could manage exercises via this endpoint.

- **Update exercise type**
  - **Method/Path**: `PATCH /exercises/{exercise_type_id}`
  - **Behavior**:
    - Accepts `ExerciseTypeUpdate` with partial fields (e.g., display name, emoji, aliases, unit, active flag).
    - Updates the corresponding `exercise_types` row.

### Challenges

- **List challenges**
  - **Method/Path**: `GET /challenges`
  - **Behavior**:
    - Returns challenges, with filters via query parameters:
      - `exercise_type_id`.
      - `is_active`.
      - Optional date filters (`starts_before`, `ends_after`).
    - Uses Supabase to query `exercise_challenges`.
  - **Response**:
    - List of `ExerciseChallengeOut` objects.

- **Get challenge by ID**
  - **Method/Path**: `GET /challenges/{challenge_id}`
  - **Behavior**:
    - Returns details of a specific challenge.
    - Includes derived fields like `total_days` and whether it is currently active based on `start_date` and `end_date`.

- **Create challenge**
  - **Method/Path**: `POST /challenges`
  - **Behavior**:
    - Accepts `ExerciseChallengeCreate`.
    - Inserts a new row into `exercise_challenges`.
    - Optionally enforces that only one active challenge per exercise type is allowed at a time (matching current expectations).

- **Update challenge**
  - **Method/Path**: `PATCH /challenges/{challenge_id}`
  - **Behavior**:
    - Accepts `ExerciseChallengeUpdate`.
    - Allows changing attributes such as `end_date`, `target_total`, `daily_target`, and `is_active`.
    - Includes validation to avoid invalid date ranges or negative targets.

### Logs

- **List logs**
  - **Method/Path**: `GET /logs`
  - **Behavior**:
    - Returns paginated log entries from `exercise_logs`.
    - Supports query parameters:
      - `exercise_type_id`.
      - `challenge_id`.
      - `date_from` and `date_to`.
      - `limit` and `offset` (with sane defaults and caps).
    - Uses Supabase queries similar to those in `get_recent_logs`, but returns normalized JSON instead of HTML text.
  - **Response**:
    - List of `ExerciseLogOut` objects plus optional pagination metadata.

- **Create log**
  - **Method/Path**: `POST /logs`
  - **Behavior (algorithm)**:
    - Validate request body against `ExerciseLogCreate`.
    - Determine `today_local` from the configured timezone if no explicit `date` is provided.
    - Identify the relevant challenge for the exercise type and date:
      - Prefer an active challenge whose dates wrap the given date; otherwise, fall back to the most recent active challenge, mirroring `get_active_challenge`.
    - Insert a new row into `exercise_logs` with the provided count and metadata, setting `challenge_id` accordingly.
    - Compute updated stats by calling the shared stats helper:
      - Recompute cumulative and today’s totals.
      - Recompute status and catch-up reps.
    - Update or insert into `user_stats` with the new totals and last logged date.
  - **Response**:
    - Returns the created log as `ExerciseLogOut` plus associated `ExerciseStatsOut` so clients can immediately refresh their UI.

- **Delete log**
  - **Method/Path**: `DELETE /logs/{log_id}`
  - **Behavior (algorithm)**:
    - Fetch the log by ID from `exercise_logs`.
    - If not found, return `404`.
    - Retrieve the exercise type and any related stats as needed.
    - Delete the log row.
    - Recompute `user_stats` totals and the last logged date for that exercise type, using the same logic as in `delete_log_entry`.
    - Optionally, recompute challenge-level stats to maintain consistency.
  - **Response**:
    - Indicates success and returns the deleted log metadata and updated stats for the affected exercise type.

### Stats

- **Get stats for all exercises**
  - **Method/Path**: `GET /stats/exercises`
  - **Behavior**:
    - For each active exercise type (or optionally filtered set):
      - Determine the relevant challenge for the current day (or a given date).
      - Call the shared stats helper to compute `ExerciseStatsOut`.
    - This mirrors the behavior where the Telegram bot shows stats for all exercises, but returns structured JSON instead of text.
  - **Response**:
    - List of `ExerciseStatsOut` entries keyed by exercise type.

- **Get stats for a single exercise**
  - **Method/Path**: `GET /stats/exercises/{exercise_type_id}`
  - **Behavior**:
    - Same as above but scoped to a single exercise type ID.
    - Supports optional query parameters for date and challenge selection.

- **Get user-level aggregated stats**
  - **Method/Path**: `GET /stats/summary`
  - **Behavior**:
    - Aggregates counts and stats across all exercise types using `user_stats`.
    - Optionally includes:
      - Total reps across all exercises.
      - Number of days with any activity.
      - Streak-like information inferred from `last_logged_date` and logs.

### Parsing and AI (optional API exposure)

- **Parse workout message**
  - **Method/Path**: `POST /workouts/parse`
  - **Behavior**:
    - Accepts a body containing raw text and optional context (e.g., language, hints).
    - Calls `parse_workout_message` to produce a `ParseResult`.
    - Does not persist anything to the database; it is purely for parsing.
  - **Note**:
    - This endpoint is optional and can be disabled or restricted more heavily, since it calls external AI.

### Jobs (existing behavior reused)

- **Trigger daily reminders (admin)**
  - **Method/Path**: `POST /jobs/daily-reminder` (kept under the existing router but documented under `Jobs` tag).
  - **Behavior**:
    - Remains largely unchanged, calling `check_daily_reminders`.
    - Documented as an internal/admin-only endpoint.

## Authentication and Authorization

- **API key scheme**
  - Use an API key provided via the `Authorization` header:
    - Support both `Bearer <key>` and raw `<key>` formats (reusing the logic from `verify_admin_key`).
  - For simplicity, the initial implementation can reuse `ADMIN_API_KEY`; if desired, introduce a separate key such as `INTERNAL_API_KEY` later, with a small change to `app.config`.

- **Scope**
  - All **write** endpoints (`POST`, `PATCH`, `DELETE`) must require a valid API key.
  - **Read-only** endpoints (`GET`) can either:
    - Require the same API key (simple, secure default), or
    - Allow anonymous access when the deployment environment is strictly internal.

- **Implementation location**
  - Define a shared dependency (similar to `verify_admin_key`) in `src/api/security.py` to avoid coupling directly to `app/routers/admin.py`.
  - Reuse that dependency across all API routers.

## OpenAPI / Swagger Documentation

- **FastAPI configuration**
  - Ensure `FastAPI` is initialized with:
    - A descriptive `title` for the API (for example, “Fitness Challenge API” rather than “Bot” only, or a combined name).
    - A `version` string aligned with the project version from `pyproject.toml`.
    - Configured `openapi_url` and `docs_url` endpoints (for example, `/openapi.json` and `/docs`).
  - Confirm that the new `src/api` routers are included in the main app so their endpoints appear in the generated OpenAPI spec.

- **Tags and grouping**
  - Define an `openapi_tags` list that describes each tag: `Exercises`, `Challenges`, `Logs`, `Stats`, `Workouts`, and `Jobs`.
  - Annotate each router and operation with appropriate tags and concise summaries to make the Swagger UI easy to navigate.

- **Request/response models**
  - Ensure every endpoint declares explicit `response_model` types so the OpenAPI schema is precise.
  - Provide example values via Pydantic `Field` metadata or FastAPI `responses`/`examples` settings, particularly for:
    - `ExerciseLogCreate`.
    - `ExerciseStatsOut`.
    - Error responses.

- **Error model**
  - Standardize error responses across endpoints by:
    - Returning JSON objects containing at least `detail` and, optionally, a machine-readable error `code`.
    - Documenting common HTTP status codes (400, 401, 403, 404, 500) in the OpenAPI schema.

## Integration with Existing App

- **Router inclusion**
  - Add a new router entry in `app/main.py` that includes the `src/api` routers under the `/api/v1` prefix.
  - Ensure imports use the proper Python package path (for example, importing from `src.api` after making `src/` a package).

- **Separation from Telegram and external services**
  - Keep Telegram-specific behavior (`send_telegram_message`, webhook handling) isolated in `app/routers/telegram.py` and `app/services/telegram_client.py`.
  - Ensure new REST endpoints do not directly send Telegram messages; they should focus on DB-backed operations and calculations.

- **No immediate DB schema changes**
  - The initial implementation will reuse existing Supabase tables and columns.
  - If future multi-user support or user authentication is added, the REST API surface and models should be ready to incorporate an explicit user or account identifier without breaking existing clients.

## Phases

### Phase 1 – Data and Service Layer

- Introduce `src/api/models.py` with API-facing Pydantic models for exercises, challenges, logs, stats, and parsing (if enabled).
- Extract shared helpers from `workout_service` into reusable functions, so that both Telegram flows and REST endpoints use the same logic.
- Implement `src/api/services.py` (or equivalent) to wrap Supabase operations for:
  - Listing and managing exercises and challenges.
  - Creating, listing, and deleting logs.
  - Computing stats for exercises and overall summary.

### Phase 2 – REST Endpoints

- Implement FastAPI routers under `src/api/` that expose the endpoints described above, mounted under `/api/v1`.
- Wire up authentication via a shared API key dependency.
- Ensure that JSON responses match the API models and that error handling is consistent.

### Phase 3 – OpenAPI Documentation and Tests

- Refine endpoint metadata (summaries, descriptions, tags, examples) to produce a clear, self-explanatory Swagger UI.
- Verify that `/docs` and `/openapi.json` expose the new REST API correctly.
- Add tests for the new endpoints using `pytest` and `pytest-asyncio`, focusing on:
  - Happy path behavior for key endpoints.
  - Authorization failures when an API key is missing or invalid.
  - Edge cases such as missing resources and invalid input.
