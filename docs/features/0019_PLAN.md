# Feature 0019 — Fix Habit Reward firing on all-rest-day (exception) days

GitHub issue #29: "Bug: Habit Reward fires on rest/exception days when no challenges are scheduled".

Habit Reward (and the Telegram `✅ Day Complete!` banner) are awarded on days when **every** active challenge treats the day as an exception/rest day (e.g. Saturday/Sunday exclusions). Logging workouts "ahead" on such a day still triggers completion + reward, even though there was no scheduled work.

Fix: if **no** challenge had scheduled work today (every challenge hit `is_today_exception`), `_check_all_challenges_complete` returns `False`.

## Root cause

`app/services/workout_service.py` → `_check_all_challenges_complete` (defined at ~L222):

- Loop over `challenges_data`; for each challenge `_compute_effective_progress` (~L181) returns `(effective_total_days, day_number, is_today_exception)`.
- `if is_today_exception: continue` (~L271) implements the Feature 0018 rule "a rest-day challenge must **not block** Habit Reward".
- When *all* challenges are rest days, the loop evaluates no challenge and falls through to `return True` at ~L281 — a vacuous success.

Call chain affected:

1. Telegram `process_incoming_message` (`app/services/workout_service.py` ~L1320) calls `_check_all_challenges_complete(challenges_data, today_local, user_id=user.id)`; on `True` it prepends `✅ <b>Day Complete!</b>` (~L1332) and fires `notify_habit_reward_if_complete` in a background task (~L1335-1342).
2. REST `POST /api/v1/logs` (`src/api/routers/logs.py` ~L186-193) fires `notify_habit_reward_if_complete(log.date, user_id=...)`.
3. `notify_habit_reward_if_complete` (~L328) calls `_check_all_challenges_complete` (~L363), then claims the date via `user_settings_repo.try_claim_habit_reward_date` and POSTs to the Habit Reward API.

Both consumers are fixed by the single change in `_check_all_challenges_complete`.

## Behavior table (from the issue)

| Scenario | Today | Result |
|---|---|---|
| All challenges are rest days | Sat with Sat/Sun exceptions | `False` → no reward, no Day Complete |
| Mix: A rest, B on track | weekday for B | `True` if B complete |
| Mix: A rest, B behind | weekday for B | `False` |
| No active challenges | any | unchanged — `_check_all_challenges_complete` already returns `False` on empty input, and `notify_habit_reward_if_complete` returns early before calling it |

## Changes

### `app/services/workout_service.py` — `_check_all_challenges_complete`

Algorithm (single pass, no extra queries):

1. Keep the existing early `return False` for empty `challenges_data`.
2. Keep the existing batch fetches (`log_repo.get_cumulative_counts_by_challenge_ids`, `challenge_exception_day_repo.list_dates_for_challenges`).
3. Introduce a local counter/flag (e.g. `scheduled_seen`) initialized to "none seen".
4. Inside the loop, keep `if is_today_exception: continue` — unchanged, so a rest-day challenge still never *blocks*.
5. For every challenge that reaches past that branch (i.e. today is scheduled work), mark `scheduled_seen` before evaluating progress; keep the existing `cumulative_total < expected` → `return False`.
6. After the loop, return `scheduled_seen` instead of the unconditional `True`. All-rest → `False`; at least one scheduled challenge that never returned `False` → `True`.

Also update the function docstring: state explicitly that a rest-day challenge does not block Habit Reward, but a day on which *every* active challenge is a rest day is not a completable day and returns `False`.

Note on the not-yet-started edge case: `challenge_repo.get_current_active(today_local, ...)` only returns challenges whose window contains `today_local`, so a non-exception challenge always has `day_number >= 1`. No extra guard on `day_number == 0` is needed; do not add one.

### Tests — `tests/services/test_reminders_rest_days.py`

`TestCheckAllChallengesCompleteRestDay` currently encodes the vacuous-true behavior. Update the class:

- Rename `test_returns_true_when_today_is_rest_day` (~L69-96) to `test_returns_false_when_all_challenges_are_rest_days` and invert the assertion: a single challenge whose today is a rest day → `_check_all_challenges_complete` returns `False`. Rewrite the assertion message (it currently claims "Rest day must short-circuit to True…") to describe the new all-rest rule: an all-rest day has no scheduled work, so it is not a completable day.
  - Change cumulative from `{1: 0}` to a large banked value (e.g. `{1: 1000}`). This is the issue's actual repro — reps logged *ahead* on a rest day — and it is what makes the test discriminating: with `{1: 0}` the expected `False` would also be produced by a build that lost the `if is_today_exception: continue` branch (`0 < expected` → `False`), so the test would pass for the wrong reason. With a banked value only the `scheduled_seen` path can yield `False`.
  - Drive today's exception through the recurring CSV path rather than a mocked explicit date: set `exception_weekdays = str(today_local.isoweekday())` (`expand_exception_dates`, `src/core/utils.py` L61-90, matches on `isoweekday()`, 1=Mon..7=Sun) and leave `list_dates_for_challenges` at the autouse `{}` default. The issue's repro is a recurring Sat/Sun exclusion, and `_check_all_challenges_complete` reaches it via `_parse_weekdays_csv` (~L263) — a branch no test in this class currently pins, since the existing tests all use `exception_weekdays=""` plus a mocked explicit date. The mixed-case tests below keep the explicit-date path, so both sources stay covered.
- Keep `test_negative_control_returns_false_without_rest_day` (~L98-125) body as-is, but fix its docstring (~L102-105): it says the control "proves the rest-day branch … is what made the previous test return `True`", which is false once the previous test asserts `False`. Restate as: the control proves the all-rest `False` comes from the rest-day branch and not from an unrelated short-circuit.
- Add `test_returns_true_when_one_challenge_rests_and_other_is_on_track`: rest-day challenge (id 1) + scheduled challenge (id 2) → `True`. Setup: both challenges use window `today-5 .. today+5`; `_mock_challenge_exception_day_repo.list_dates_for_challenges = AsyncMock(return_value={1: {today_local}})` (id 2 has no exceptions); challenge 1 `daily_target=50` (any value — it is skipped by `continue` before `daily_target` is used, so it must not affect the result), challenge 2 `daily_target=10`. With no exceptions on id 2, `_compute_effective_progress` gives `day_number = (today - (today-5)).days + 1 = 6`, and `calculate_expected_progress` (`src/core/utils.py` L7-20) is `daily_target * day_number`, so the threshold is `10 * 6 = 60`. `mock_log_repo.get_cumulative_counts_by_challenge_ids` returns `{1: 0, 2: 100}` → `100 >= 60` → `True`.
- Add `test_returns_false_when_one_challenge_rests_and_other_is_behind`: identical setup, but cumulative `{1: 0, 2: 0}` → `0 < 60` → `False`. This pins that the mixed-case rest challenge still does not force success.

No new test is added for the Telegram banner consumer. `process_incoming_message` has no completion logic of its own: it binds `all_complete` directly from `_check_all_challenges_complete` (~L1320-1324) and the `✅ <b>Day Complete!</b>` append plus the background `notify_habit_reward_if_complete` task are both gated on that single boolean (~L1331-1342). Helper-level coverage is therefore sufficient; this is a recorded, accepted gap rather than an oversight.

Docstring updates in the same file (they encode the pre-fix semantics and would otherwise mislead a future reader chasing an 0018 regression):

- Module docstring (L1-17): it currently says all three functions share the same `if is_today_exception: continue` outcome and that each test pins "the rest-day branch (today is a rest day → no work happens)". Restate for `_check_all_challenges_complete`: the `continue` still means a rest-day challenge never blocks, but a day on which *every* challenge rests now returns `False` rather than a vacuous `True`. The evening-reminder / daily-reminder functions keep the old "no work happens" outcome.
- Class docstring `TestCheckAllChallengesCompleteRestDay` (L66-67): currently "must skip rest-day challenges so they cannot block Habit Reward". Extend to the two-part rule — a rest-day challenge never *blocks*, but an all-rest day is not completable and returns `False`.

Fixtures/patterns to reuse: the autouse `_mock_challenge_exception_day_repo` fixture in `tests/services/conftest.py` (defaults to no exception days) and the `patch("app.services.workout_service.log_repo")` pattern already used in this file. Challenge inputs to `_check_all_challenges_complete` are plain dicts (`id`, `start_date`, `end_date`, `daily_target`, `exception_weekdays`), not the `SimpleNamespace` helper used by the reminder tests.

Other suites are unaffected: `tests/services/test_habit_reward_client.py` patches `_check_all_challenges_complete` itself, and `tests/api/test_services_exception_stats.py` exercises `compute_exercise_stats` in `src/api/services.py`, which is not touched.

### `RULES.md`

Add a short note under `## Habit Reward Integration (Feature 0011)` → `### How It Works` (~L1087-1097), in the step describing `_check_all_challenges_complete`:

- A challenge whose today is an exception/rest day never blocks Habit Reward (Feature 0018).
- If **every** active challenge is on an exception/rest day today, the day is not completable: `_check_all_challenges_complete` returns `False`, so no Habit Reward and no `✅ Day Complete!`, even when reps were banked ahead.

Mirror one line of the same rule in `### Completion Logic` (~L741-753), which currently states only "Shows `✅ Day Complete!` when ALL active challenges are on track or ahead".

## Risk / user-visible impact

1. **Habit Reward streaks will gap on all-rest days.** No completion POST is sent on an all-rest day, so the external Habit Reward service's `streak_count` — the value the bot renders back via `_format_habit_reward_message` (~L299-301) as `{"🔥" * min(streak_count, 5)} <b>Streak:</b> N days` — resets for users on e.g. a weekday-only challenge, where it previously kept counting through the weekend. Accepted: this is the direct point of issue #29. If streak continuity matters, the user configures matching rest days on the Habit Reward side.
2. **No habit-reward date claim on all-rest days.** `notify_habit_reward_if_complete` now returns `True` early without calling `user_settings_repo.try_claim_habit_reward_date`, so those dates are never marked claimed. Intentional — nothing was awarded, so nothing needs deduping.
3. **Per-challenge `✅` and REST `is_daily_complete` intentionally unchanged.** On an all-rest day the per-exercise checkmarks from `get_exercise_stats_and_message` and the REST `is_daily_complete` flag still read complete while the `✅ Day Complete!` banner disappears. This divergence is deliberate (`src/api/services.py` is out of scope); do not "fix" it as part of this change.

## Out of scope

- Changing how banked reps on rest days affect cumulative progress (intentional today).
- Changing evening reminders (`compute_evening_reminder`, `check_daily_reminders`) — they already skip rest days correctly.
- Backfilling / clawing back Habit Rewards already sent on past rest days.
- `src/api/services.py` `compute_exercise_stats` / `is_daily_complete` per-exercise flag.
