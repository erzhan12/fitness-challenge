# Feature 0010: Multi-User Support

## Brief

The project is currently single-user: `ExerciseType`, `ExerciseChallenge`, `ExerciseLog`, and `UserStats` have no user ownership, and settings are stored in a singleton `AppSettings` row (`src/core/models.py`, `src/core/repositories.py`). This plan adds multi-user support across the database, REST API, and Telegram flows (using `app_users` + `user_settings` tables).

Verbatim requirements from the prompt:
- “Design database schema (users, user_settings tables)”
- “Add `users` table (telegram_user_id, username, first_name, timezone, created_at, settings) (django already has Users table, think about extending it or creating additional model with one to one reference type)”
- “Add `user_id` foreign key to exercise_logs, exercise_challenges, exercise_types (other models if needed)”
- “Create `/api/v1/users` endpoints (POST register, GET profile, PATCH update)”
- “Implement user registration flow in Telegram - send message to a superuser and wait for approval, once they approves then continue register”
- “Update all stats calculations to be user-scoped”
- “Add user context to all API endpoints”
- “Create database migration scripts”
- “Add comprehensive unit tests”
- “Update existing tests to work with multi-user”
- “Update all existing documentation”

## Phase 1 — Data Layer (Django Models + Schema)

### 1.1 `users` table

Implement a dedicated application user model (recommended) rather than changing Django’s auth model:
- Create a new Django model in `src/core/models.py` (e.g., `AppUser`) with `db_table = "app_users"`.
- Keep Django admin/auth users (`auth_user`) separate from app users to avoid custom auth migrations.

Fields (matches the prompt verbatim; add minimal extras for approval flow):
- `telegram_user_id` (unique)
- `username` (nullable/blank)
- `first_name` (nullable/blank)
- `timezone` (string; default to current `settings.TZ`)
- `created_at` (timestamp)
- `settings` (JSON for extensibility)
- Approval state needed for “wait for approval”:
  - `status` (e.g., `pending` / `approved` / `rejected`) or `is_approved` boolean + timestamps

### 1.2 `user_settings` table

Create a per-user settings model (e.g., `UserSettings`) with `db_table = "user_settings"` and a 1:1 relationship to the user:
- `user_id` (OneToOne FK to `app_users`)
- `telegram_chat_id` (where to send reminders and replies)
- `is_reminder_active`
- Per-user idempotency for evening reminders (moves off the singleton `AppSettings`):
  - `last_reminder_21_date`, `last_reminder_22_date`, `last_reminder_23_date`

If you want to keep an app-wide toggle later, keep `AppSettings` for “global” values only; otherwise plan to stop using `AppSettings` in runtime code and treat it as legacy data to migrate once.

### 1.3 Add `user_id` foreign keys to domain tables

Update existing models in `src/core/models.py`:
- `ExerciseType` add `user_id`
- `ExerciseChallenge` add `user_id`
- `ExerciseLog` add `user_id`
- `UserStats` must become `(user_id, exercise_type_id)`-scoped (current OneToOne with `ExerciseType` is single-user by design)

Constraints to revisit:
- `ExerciseType.name` is globally `unique=True` today. With per-user types, make uniqueness per user instead (composite uniqueness on `(user_id, name)`).
- `UserStats` should be unique per `(user_id, exercise_type_id)`.

### 1.4 Migrations/backfills (schema + existing data)

Create new Django migrations in `src/core/migrations/` that:
1. Add `app_users` and `user_settings` tables.
2. Add nullable `user_id` columns to existing tables.
3. Backfill existing single-user rows to a “default/legacy” user (create one user row and assign all existing `exercise_*` and `user_stats` rows to it; copy `AppSettings` values into that user’s `user_settings`).
4. Make `user_id` non-nullable and add the composite uniqueness constraints.

## Phase 2 — Repository Layer (User-Scoped Queries)

Update `src/core/repositories.py` so every read/write is user-scoped:
- Add a required `user_id` (or `user`) parameter to repository methods, rather than relying on ad-hoc filter dicts.
- Ensure “by id” lookups (`get_by_id`) also verify ownership (e.g., log deletion must not delete another user’s log).

Concrete touchpoints:
- `ExerciseTypeRepository.get_all/get_by_id/get_by_name/create/update/get_by_ids`
- `ExerciseChallengeRepository.get_all/get_by_id/get_active_for_type/get_current_active/create/update`
- `ExerciseLogRepository.get_all/get_by_id/get_cumulative_count/get_today_count/get_last_log/get_*_by_challenge_ids/create/delete`
- `UserStatsRepository.get_all/get_by_exercise_type/get_or_create/increment_total/decrement_total/sync_last_logged_date`
- Replace or mirror `AppSettingsRepository` with a `UserSettingsRepository` that operates on `user_id` (including idempotency claim/clear helpers currently in `AppSettingsRepository`).

## Phase 3 — REST API (User Context + `/api/v1/users`)

### 3.1 Add `/api/v1/users` endpoints

Create `src/api/routers/users.py` and include it in `app/main.py` under `/api/v1`.

Endpoints (as requested):
- `POST /api/v1/users` (register)
  - Accepts `telegram_user_id`, `username`, `first_name`, `timezone`, and optional `settings`
  - Creates user in “pending” state by default (aligns with Telegram approval flow)
- `GET /api/v1/users` (profile)
  - Returns current user profile + status + selected settings (or embed `user_settings`)
- `PATCH /api/v1/users` (update)
  - Allows updating `username`, `first_name`, `timezone`, and `settings` (and optionally user_settings fields if you want a single endpoint)

Add corresponding Pydantic models in `src/api/models.py` (e.g., `UserOut`, `UserRegister`, `UserUpdate`).

### 3.2 “Current user” resolution for all endpoints

Add a shared dependency (recommended location: `src/api/security.py`) that resolves the current user and enforces approval:
- Input: a “user context” identifier in headers (choose one consistent mechanism):
  - Option A (Telegram-aligned): `X-Telegram-User-Id` and (optional) `X-Telegram-Chat-Id`
  - Option B (internal/admin aligned): `X-User-Id` (internal DB id)
  - Option C (more secure for external clients): per-user API key/token stored in DB and supplied via `Authorization`
- Output: `AppUser` (or `{user_id, timezone, chat_id}` struct)
- Behavior: if user is missing or not approved, return 401/403 (and ensure Telegram flow is the one that advances approval).

### 3.3 Thread `user_id` through all API routes/services

Update `src/api/routers/*` to take `current_user = Depends(get_current_user)` and pass `current_user.id` to services:
- `src/api/routers/exercises.py` → `list_exercise_types/get_exercise_type/create_exercise_type/update_exercise_type`
- `src/api/routers/challenges.py` → `list_challenges/get_challenge/create_challenge/update_challenge`
- `src/api/routers/logs.py` → `list_logs/get_log/create_log/delete_log`
- `src/api/routers/stats.py` → `compute_exercise_stats/get_all_exercise_stats/get_stats_summary`
- `src/api/routers/workouts.py` → `list_exercise_types/list_current_active_challenges` (parser inputs must be user-scoped)
- `src/api/routers/settings.py` → interpret settings as per-user (read/update `user_settings`, not the singleton `AppSettings`)

Update `src/api/services.py` signatures similarly (add `user_id` parameter) for:
- `list_exercise_types`, `get_exercise_type`, `create_exercise_type`, `update_exercise_type`
- `list_challenges`, `get_challenge`, `get_active_challenge_for_type`, `list_current_active_challenges`
- `list_logs`, `get_log`, `create_log`, `delete_log`
- `compute_exercise_stats`, `get_all_exercise_stats`, `get_stats_summary`
- `get_settings`, `update_settings` (become per-user settings)

## Phase 4 — Telegram Registration + Approval Flow

### 4.1 Capture sender identity in webhook

Update `app/routers/telegram.py` `telegram_webhook()`:
- Extract `telegram_user_id`, `username`, `first_name` from `update.message.from_`
- Pass these to `process_incoming_message()` (or a new “telegram dispatcher” function) along with `chat_id`
- Stop writing global `AppSettings.telegram_chat_id`; instead update the current user’s `user_settings.telegram_chat_id`

### 4.2 Registration gating in `process_incoming_message()`

In `app/services/workout_service.py` `process_incoming_message()`:
1. Resolve `AppUser` by `telegram_user_id`.
2. If user does not exist:
   - Create a user row with status `pending` and store `username/first_name/timezone`
   - Create `user_settings` with `telegram_chat_id = chat_id`
   - Notify the superuser for approval (see below)
   - Reply to the requester that registration is pending approval
3. If user exists but is not approved:
   - Reply “pending approval” (and optionally re-send/refresh the approval request on a cooldown)
4. If user is approved:
   - Proceed with normal workout parsing/logging using that user’s scoped data

### 4.3 Admin approval via Telegram commands

Add a minimal approval protocol handled by `process_incoming_message()`:
- Commands in an admin chat (or from admin user IDs):
  - `/approve <telegram_user_id>`
  - `/reject <telegram_user_id>`

Algorithm:
1. Verify the sender is a “superuser” (configure via env var list, or store `is_admin` on a user row).
2. Parse the target `telegram_user_id`.
3. Transition the target user status:
   - `pending → approved` (record `approved_at`)
   - or `pending → rejected` (optional reason)
4. Notify the target user’s `telegram_chat_id` that they are approved/rejected.

Configuration touchpoint:
- Add a dedicated env var in `app/config.py` (e.g., admin telegram user IDs / admin chat id) so approvals can be restricted without relying on the legacy `TARGET_CHAT_ID`.

## Phase 5 — User-Scoped Stats, Logs, Challenges, Reminders

### 5.1 User-scoped stats

Update stats computations so they only consider the current user’s data:
- `src/api/services.py` `compute_exercise_stats()` must pass `user_id` into:
  - challenge lookup (`get_active_challenge_for_type`)
  - log aggregates (`log_repo.get_cumulative_count`, `log_repo.get_today_count`)
- `src/api/services.py` `get_stats_summary()` must count distinct days and totals for that user only (avoid `log_repo.get_all(limit=10000)` without user filter).

### 5.2 User-scoped Telegram log operations

In `app/services/workout_service.py`:
- `get_exercise_types()`, `list_current_active_challenges()` inputs must be user-scoped
- `get_recent_logs()`, `undo_last_log()`, `delete_log_entry()` must only access/delete the current user’s logs
- When creating logs, include `user_id` (and ensure stats updates hit the correct user’s `UserStats` row)

### 5.3 Per-user reminders and idempotency

Refactor reminder sending so it runs for each approved user with reminders enabled:
- Replace reads of `app_settings_repo.get_singleton()` with per-user `user_settings_repo.get_by_user_id()`
- Idempotency (`try_mark_hour_sent`, `clear_hour_sent`) must be per-user per-hour (store on `user_settings`)
- `send_evening_reminder()` and legacy `check_daily_reminders()` should iterate users rather than sending to one `telegram_chat_id`

If user timezones need to be honored:
- Evaluate whether `app/services/reminder_scheduler.py` should schedule per-user (or run a frequent loop and check “is it 21/22/23 in user TZ now?”).
