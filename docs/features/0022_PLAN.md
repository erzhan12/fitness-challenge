# Feature 0022 — Per-user editable reminder hours + JSON idempotency

GitHub issue #34. Move reminder hours to per-user `UserSettings.reminder_hours` (Django admin only, default `[13, 21, 22]`), store send idempotency as `last_reminder_sent_dates` JSON map on `UserSettings`, and cut the live reminder path fully off `AppSettings` onto `UserSettings`. Default list adds `13` and drops `23` from the *default only* — any hour `0–23` remains valid if configured. Empty `reminder_hours` means no sends (no fallback to default); `[]` is only a meaningful opt-out **after** migration backfill (see Phase 1). No global `TARGET_CHAT_ID` fallback on send — per-user `telegram_chat_id` required.

## Current state

- `REMINDER_HOURS = [21, 22, 23]` in `app/constants.py`.
- `reminder_scheduler.get_next_reminder_time()` and `start_reminder_scheduler()` sleep on that fixed list.
- `send_evening_reminder(reminder_hour)` reads `app_settings_repo.get_singleton()` for `is_reminder_active`, `telegram_chat_id` (with `settings.TARGET_CHAT_ID` fallback), and `try_mark_hour_sent` / `clear_hour_sent` on `last_reminder_{21,22,23}_date`.
- `compute_evening_reminder(today_local, reminder_hour)` calls `challenge_repo.get_current_active(today_local)` **without** `user_id` — returns all users' challenges.
- `UserSettings` already has `is_reminder_active`, `telegram_chat_id`, and unused per-user `last_reminder_{21,22,23}_date` columns; `UserSettingsRepository` has column-based `try_mark_hour_sent` / `clear_hour_sent` / `check_already_sent` (not used by live send path).
- Live idempotency is written only to `app_settings.last_reminder_{21,22,23}_date` (filled in prod). `user_settings` per-hour date columns may contain stale copies from migration `0004_backfill_default_user` (copied from `app_settings` at backfill time) but are unused by the live send path — data cutover migration `0011` must read authoritative state from `app_settings`, not existing `user_settings` columns.
- Live send honors `app_settings.is_reminder_active` as a global kill switch; per-user `user_settings.is_reminder_active` may still be `True` while global is `False` — migration `0011` must propagate singleton `False` to all `user_settings` before dropping the column.
- Live send uses `app_settings.telegram_chat_id` (filled in prod); per-user `user_settings.telegram_chat_id` may be null/stale — migration `0011` must copy the singleton chat id onto the default user (`telegram_user_id=0`) before dropping the column, or reminders stop after cutover.
- Live send has **no** `AppUser.Status.APPROVED` gate — it reads the singleton `app_settings` row only. New per-user query helpers (`get_users_for_reminder_hour`, `get_distinct_active_reminder_hours`) **intentionally** restrict to `user__status=APPROVED` plus non-null `telegram_chat_id` and non-empty `reminder_hours` (behavioral tightening vs today's singleton path).
- Settings API (`get_settings` / `update_settings` in `src/api/services.py`) already uses `user_settings_repo` for `is_reminder_active` and `telegram_chat_id`.
- **Database (locked for this feature):** production deploy and local/dev use **SQLite** (`DATABASE_URL=sqlite:////app/data/db.sqlite3` in deploy; `data/db.sqlite3` locally). Implement and test only the SQLite path.

### Migration operations

**Pitfall:** `AddField(..., default=list)` (or any empty default) materializes `[]` on every existing row. Those rows then no longer “lack” a value, so a follow-up “set defaults where empty/missing” step either no-ops or treats accidental `[]` as opt-out. Fix by using the callable default **and** unconditionally backfilling hours on **all** existing rows (`0011` `RunPython`).

## Phase 2 — Repository layer (`src/core/repositories.py`)

### `UserSettingsRepository`

**Replace** column-based idempotency helpers with JSON-map versions:

- `try_mark_hour_sent(user_id, target_date, hour)` — set `last_reminder_sent_dates[str(hour)] = target_date.isoformat()` only if that key is missing or not equal to today. Return `True` if this call won (`cursor.rowcount == 1` / ORM update count), `False` otherwise. **Key-merge semantics (locked):** must **merge** one hour key into the existing JSON object — **forbid** assigning a full replacement dict that would erase other hour keys.
  - **Required implementation = one conditional SQLite `UPDATE`:** use SQLite JSON functions in SQL (e.g. `json_set` to merge the key, `json_extract` / `->>`-equivalent in `WHERE` so the row updates only when the key is absent or `!= today`). Example shape (illustrative, not final SQL): `UPDATE user_settings SET last_reminder_sent_dates = json_set(COALESCE(last_reminder_sent_dates, '{}'), '$.' || :hour_key, :today) WHERE user_id = :uid AND (json_extract(last_reminder_sent_dates, '$.' || :hour_key) IS NULL OR json_extract(...) != :today)`. This is the same class of race-safe claim as today's scalar `.exclude(...).update(...)`.
  - **Do not** use `transaction.atomic()` + `select_for_update()` + Python read-modify-write as the claim algorithm: SQLite **ignores** `select_for_update()`, so that pattern does **not** guarantee a single winner and would contradict the concurrent-claim test.
  - A naive `.update(last_reminder_sent_dates={str(hour): ...})` that replaces the whole column is **forbidden**.
- `clear_hour_sent(user_id, target_date, hour)` — remove or clear key `str(hour)` when its value equals `target_date.isoformat()` (rollback on send failure), also via conditional SQLite JSON UPDATE (e.g. `json_remove` with matching `WHERE`), not unlocked RMW.
- `check_already_sent(user_id, target_date, hour)` — read map key `str(hour)`.

Remove `_get_reminder_field_name` and `REMINDER_HOURS` membership checks from idempotency methods — any int hour `0–23` is valid at claim time; hour membership for *sending* is enforced upstream via `reminder_hours`.

**Add query helpers for scheduler/send:**

- `get_distinct_active_reminder_hours() -> List[int]` — union of `reminder_hours` across rows where `is_reminder_active=True`, `user__status=APPROVED`, non-empty `reminder_hours`, and `telegram_chat_id` is not null. Used only for next-wake calculation.
- `get_users_for_reminder_hour(hour: int) -> List[UserSettings]` — filter `is_reminder_active=True`, `user__status=APPROVED`, `telegram_chat_id__isnull=False`, and hour membership in `reminder_hours`. Do **not** filter by whether hour is in `DEFAULT_REMINDER_HOURS`.

**Hour membership on SQLite (required):** Django’s JSON `contains` lookup is **not** reliable for array membership on SQLite. Implement explicitly, e.g. `json_each(reminder_hours)` via `RawSQL` / `extra()`, **or** narrow with shared non-JSON filters in ORM then filter `hour in row.reminder_hours` in Python. Do **not** rely on `reminder_hours__contains=[hour]` as the sole path.

**Update** `get_or_create` / defaults so new rows get `reminder_hours=[13, 21, 22]` and `last_reminder_sent_dates={}`.

**Extend** `get_users_with_reminders_enabled` if still referenced — align filters with the send path (non-empty `reminder_hours`).

## Phase 3 — Scheduler (`app/services/reminder_scheduler.py`)

Refactor `get_next_reminder_time()`:

1. Load distinct hours via `user_settings_repo.get_distinct_active_reminder_hours()` (make function `async` or accept pre-fetched hours from caller).
2. If the union is empty, use `DEFAULT_REMINDER_HOURS` for sleep timing only (no sends until users exist).
3. Among today's upcoming hours in the union, pick the earliest; if all passed today, schedule the earliest hour tomorrow.
4. Return `(next_datetime, hour)`.

**Bounded schedule re-evaluation (required):** admin can change `reminder_hours` while the scheduler is sleeping. A one-shot sleep until the previously computed next hour would miss a newly added earlier hour (e.g. noon plans 21:00; at 13:00 admin adds 14:00 → must fire at 14:00, not wait until 21:00).

**Critical ordering (locked):** `get_next_reminder_time()` only returns hours with `reminder_time > now` (strict). Recomputing at or after the target wall-clock (e.g. sleep crosses 14:00:00) therefore **skips** that hour and jumps to the next future one. The locked target must be checked for due **before** any configuration re-evaluation replaces it.

`start_reminder_scheduler()` loop (required order):

1. Compute initial `(current_target_time, current_hour)` and keep them as the **locked** target.
2. Re-read `now = datetime.now(TZ)`.
3. **Stale locked target (required — clock jump / long suspend):** if `current_target_time.date() < now.date()` (both in `settings.TZ`), the locked window is for a prior calendar day. Log at `warning` (include locked datetime and current `now`), **do not** call `send_evening_reminder` — `send_evening_reminder` always derives `today_local` from send-time `now`, so firing here would claim **today's** idempotency slot and evaluate **today's** challenges while silently dropping yesterday's intended send. Discard the stale lock and replace via `get_next_reminder_time()`, then `continue` the loop. **No catch-up sends** for missed prior-day windows (out of scope; operators rely on manual `/jobs/daily-reminder` if needed).
4. **Due send:** **if `now >= current_target_time`:** call `send_evening_reminder(current_hour)` for that locked target (exactly once from the scheduler's point of view), then compute a fresh next locked target and `continue`. Do not recompute/replace `current_hour` before this send.
5. **Else** (`current_target_time` still in the future): sleep one bounded step (`HEARTBEAT_INTERVAL_SECONDS`).
6. **After the sleep returns:** go to step 2 (re-read `now`, stale check, then due send or config re-evaluation).
7. **Config re-evaluation** (only when step 4 did not fire and step 5 slept — i.e. locked target still future after step 3): call `get_next_reminder_time()`. If the new next is earlier than the locked target (or a different earlier hour appeared), replace the locked target; otherwise keep it.
8. Do **not** send solely because the heartbeat fired; send only when the locked target is due (step 4).
9. A due retargeted hour must be sent **exactly once** (idempotency still applies inside `send_evening_reminder`; the scheduler must not skip the hour by recomputing past it).

Update module docstrings (no longer hard-coded 9/10/11pm only).

Keep expired-challenge sweep (`deactivate_expired_challenges`) first, fail-open, all users, once per wake.

Then **per-user loop** (new helper e.g. `_send_evening_reminder_for_user(user_settings, reminder_hour)` acceptable):

1. Load candidates: `user_settings_repo.get_users_for_reminder_hour(reminder_hour)`.
2. For each user:
   - Skip if no `telegram_chat_id` — **no** `settings.TARGET_CHAT_ID` fallback.
   - Skip if `not is_reminder_active` (already filtered, but guard if helper reused).
   - Atomic claim: `user_settings_repo.try_mark_hour_sent(user_id, today_local, reminder_hour)`.
   - `compute_evening_reminder(today_local, reminder_hour, user_id=user_id)`.
   - If `should_send`: `send_telegram_message(telegram_chat_id, message_html, parse_mode="HTML")`.

   - On unexpected exception in this user's compute/send path: `clear_hour_sent` for that user/hour/date, **`logger.exception`**, then **continue** to remaining users. Do **not** re-raise out of the per-user loop — today's single-user `send_evening_reminder` re-raises after clear (`workout_service.py` ~L1634), but carrying that into a multi-user loop would let one broken user block all later users for that hour.
   - If nothing to send (`should_send=False`): retain claim (same as today — prevents recompute spam).
3. Stale JSON keys (e.g. migrated `"23"`) are never read for claims; keys for hours removed from `reminder_hours` may remain and are ignored.
4. Outer function returns normally after the loop (failures are per-user, logged). Scheduler / admin job must not see a raised exception from one bad user.
