# Feature 0020 — No fake stats when no in-window challenges; auto-clear expired `is_active`

GitHub issue #31: When no challenge falls in today's date window (`is_active=True` AND `start_date ≤ today ≤ end_date`), Telegram workout replies fall back to every active exercise type and render fake progress cards (`Day 1/30`, target `990`). Expired challenges often remain `is_active=True` in admin even though date filtering already excludes them.

Implement **both** parts from the issue: (1) stop the all-exercise-types fallback; (3) auto-clear `is_active` when `end_date` has passed.

## Root cause

**Telegram (`app/services/workout_service.py` → `process_incoming_message`, ~L1129–1145):**

1. `list_current_active_challenges(today_local, user_id=user.id)` delegates to `challenge_repo.get_current_active` (`src/core/repositories.py` ~L438–449), which filters `is_active=True` **and** `start_date ≤ today ≤ end_date`.
2. When that returns empty, the code falls back to `get_exercise_types(user.id)` (all active exercise types) with an empty `challenge_map`.
3. After parsing, step "4. Process Remaining Exercises" (~L1309–1325) iterates every `exercise_type` and calls `get_exercise_stats_and_message` with `challenge=None`.
4. `compute_exercise_stats` (`src/api/services.py` ~L964–971) applies hardcoded defaults when `challenge` is absent: `day_number=1`, `total_days=30`, `daily_target=33` → `target_total=990`.

**REST (`src/api/routers/workouts.py` → `parse_workout`, ~L84–97):**

- Fetches `list_exercise_types(..., challenge_only=True)`; if empty, falls back to `challenge_only=False` (all active types).
- `challenge_only` itself (`src/api/services.py` ~L113–120) keys off `challenge_repo.get_all(filters={"is_active": True})` — **not** the date window — so expired-but-still-flagged challenges can keep types in the parser list even when `get_current_active` is empty.

**Data hygiene:** No existing `deactivate_expired` path. `archive_challenge` is documented in `RULES.md` but not implemented under `src/`. Expired rows stay `is_active=True` until manually unchecked.

## Part 1 — Stop the all-exercise-types fallback

### Policy (Telegram and REST must match)

| `list_current_active_challenges` result | Behavior |
|---|---|
| ≥1 in-window challenge | Unchanged: restrict to those challenges' exercise types; existing multi-challenge / multi-number mapping |
| Empty | Do **not** call `get_exercise_types()` / all-types fallback. Return a clear "no active challenges" response. Do **not** parse, log, or render status cards. |

User-facing copy (verbatim from issue): **"No active challenges right now. Create one with /challenge or extend an existing challenge's dates."**

### `app/services/workout_service.py` — `process_incoming_message`

After fetching `challenges_data` (~L1129):

1. **Early exit when empty:** If `not challenges_data`, `await send_telegram_message(chat_id, ...)` with the copy above and `return`. Place this **before** exercise-type resolution, parsing, logging, and the "remaining exercises" loop.
2. **Remove fallback block** (~L1137–1146): delete the branch that calls `get_exercise_types(user.id)` when `challenge_type_ids` is empty.
3. **Keep the non-empty path** (~L1147–1163): derive `exercise_types` from `challenge_type_ids` via `exercise_type_repo.get_by_ids`, filter `is_active`, build `challenge_map` — unchanged.
4. **Numbers-only fast path** (~L1180–1185) already errors on empty `challenges_data`; no change needed beyond the early exit making it unreachable for the general case.

`compute_exercise_stats` defaults (~L967–971) stay as-is for other callers (e.g. stats endpoints); the workout flow must never reach them without a challenge after this change.

### `src/api/routers/workouts.py` — `parse_workout`

Reorder and align with Telegram:

1. Fetch `challenges_data = await list_current_active_challenges(...)` **first** (move before exercise-type fetch).
2. If `not challenges_data`, return `ParseWorkoutResponse(entries=[], is_valid=False, error_reason=<same copy as Telegram>)` immediately — no parser call.
3. **Remove** the `challenge_only` → all-types fallback (~L84–97).
4. Build `api_exercise_types` from in-window challenge type IDs only (mirror Telegram: `get_by_ids`, then **filter `is_active` on the returned types** exactly as the Telegram path does at §Part 1 step 3). Do not use `challenge_only=True` on `is_active`-only challenges. Keeping the `is_active` filter parallel to Telegram avoids an active challenge tied to a deactivated exercise type leaking into parser scope on only one of the two surfaces.
5. Existing numbers-only and `parse_workout_message` paths below stay unchanged when challenges exist.

### Out of scope for Part 1

- `list_exercise_types(challenge_only=True)` filter semantics (still `is_active`-based). Part 3 deactivation reduces staleness; parse endpoint no longer depends on it.
- `determine_default_exercise` "no challenges → pushups" fallback — irrelevant once parse is gated on non-empty `challenges_data`.
- **Direct `POST /api/v1/logs` (`create_log` in `src/api/services.py` ~L1208+):** unchanged. It still calls `compute_exercise_stats` without gating on in-window challenges and will continue to emit `day_number=1`, `target_total=990` defaults when `get_active_challenge_for_type` returns `None`. Fake stats on that path are not addressed in this feature.

## Part 3 — Auto-clear `is_active` when `end_date` has passed

Explicit date-expiry deactivation only. **Not** the old 100%-progress auto-archive.

| Trigger | Behavior |
|---|---|
| `end_date < today` (local TZ) and `is_active=True` | Set `is_active=False`; if `is_default=True`, also set `is_default=False` |
| Scope | Per-user when `user_id` provided; all users when `user_id` is `None` |
| Idempotency | Rows already `is_active=False` are not selected |

### `src/core/repositories.py` — `ExerciseChallengeRepository`

Add `deactivate_expired(self, reference_date: date, user_id: Optional[int] = None) -> int`:

0. **Decorate with `@sync_to_async`** like every sibling method (`get_current_active`, `create`, …). The Django ORM `.filter().update()` calls are synchronous; without the decorator, `await challenge_repo.deactivate_expired(...)` raises `TypeError: object int can't be used in 'await' expression`.
1. Query `ExerciseChallenge.objects.filter(is_active=True, end_date__lt=reference_date)`.
2. If `user_id is not None`, add `.filter(user_id=user_id)`.
3. Bulk update in one query: `is_active=False`; for rows with `is_default=True`, set `is_default=False` (use `update(is_active=False, is_default=False)` on the queryset — safe for rows already `is_default=False`).
4. Return updated row count (for optional debug logging).

### `src/api/services.py` — shared helper + lazy call site

Add `async def deactivate_expired_challenges(target_date: Optional[date] = None, user_id: Optional[int] = None) -> int` that resolves `reference_date` and calls `challenge_repo.deactivate_expired`.

**Cutoff design (one rule, no ambiguity).** The helper's `target_date` parameter *is* the cutoff: `reference_date = target_date or datetime.now(TZ).date()`, then `deactivate` selects `end_date < reference_date`. The rule is about **call sites**, not about ignoring the param:

- **Every production call site passes NO date argument** → cutoff defaults to real today. This includes the `list_current_active_challenges` sweep and the evening-reminder sweep.
- **Never thread `list_current_active_challenges`'s local `current_date` (`= target_date or today`) into the sweep.** A caller asking "what was active on some future/past date" must not deactivate still-running challenges against that display date. So the sweep call inside `list_current_active_challenges` is `await deactivate_expired_challenges(user_id=user_id)` — no date.
- **Only unit tests pass an explicit `target_date`**, to pin a deterministic cutoff without patching the clock.

**Call inside `list_current_active_challenges` (~L264):** Before `get_current_active`, invoke the sweep for that user. **Wrap it in `try/except` and fail open** — this helper is on the hot read path (only two callers: the Telegram workout handler at `workout_service.py:1129` and REST `parse_workout` at `workouts.py:114`). A transient DB error during the hygiene write must be logged (`logger.exception`) and swallowed, never propagated, so it cannot break workout logging or `/parse`. Data hygiene is best-effort; the date-window read below is the source of truth.

### Periodic call site — evening reminder sweep

**`app/services/workout_service.py` → `send_evening_reminder` (~L1566):** After `_ensure_orm()` and before the settings/`is_reminder_active` checks, sweep all users once per reminder hour (no `user_id`). Idempotent; cheap when nothing is expired.

Two placement gotchas:

1. **`today_local` is not defined yet at that point** — it is currently computed at `workout_service.py:1596`, *after* the settings and `chat_id` guards. Do **not** write `deactivate_expired_challenges(today_local)` before L1596 (would raise `NameError`). Either call the helper with **no date argument** (it derives real today itself — the recommended form given the cutoff rule above), or hoist a local `today_local = datetime.now(TZ).date()` above the sweep. Recommended: call `await deactivate_expired_challenges()` with no arguments.
2. **Wrap the sweep in `try/except` (fail open).** It sits *before* the existing `try` block at `workout_service.py:1604`, so an unhandled exception here would abort `send_evening_reminder` even when reminders are disabled/unconfigured. Log via `logger.exception` and continue; the hygiene sweep must never block or crash the reminder path.

Do **not** add deactivation to `compute_evening_reminder` itself — keep side effects in the send/sweep entry point.

Date-window filtering (`get_current_active`) remains the source of truth for what Telegram shows; auto-clear is admin/data hygiene.

### Part 3 — expiry deactivation

**Service unit tests** — the file `tests/api/test_services.py` does **not** exist yet (only `tests/api/test_services_exception_stats.py`). **Create `tests/api/test_services.py`** (new file, mocked-repo style matching the existing suite):

- Mock `challenge_repo.deactivate_expired` on `deactivate_expired_challenges`: returns updated count. Two cases: (i) no-arg call → assert `reference_date` equals real today and `user_id` forwarded (the production path); (ii) explicit `target_date=` call → assert that exact date is forwarded as the cutoff (the test-injection pin the cutoff rule allows).
- `list_current_active_challenges` calls the sweep before `get_current_active` (ordering).
- Sweep failure is swallowed: make `deactivate_expired` raise; assert `list_current_active_challenges` still returns the `get_current_active` result (fail-open contract).
- Scenarios via mock return values / call assertions: expired+active → deactivation invoked; already inactive → count 0; `user_id` forwarded; idempotent second call → count 0.

**Integration-style (mocked):** After `deactivate_expired` mock clears a row, `get_current_active` no longer returns it (confirms wiring, not ORM).

**Repository-level test for the bulk mutation (mocks cannot cover this).** The correctness lives entirely inside `ExerciseChallengeRepository.deactivate_expired` — the `filter(is_active=True, end_date__lt=…)` predicate, `user_id` scoping, and `is_default` clearing — which mocked service tests bypass.

**Infra prerequisite (this repo has none today):** there is currently **no** ORM/DB-backed test — no `pytest-django`, no `django_db` marker, no `TestCase`; every existing test uses fully mocked repos (`tests/core/` holds only pure `test_utils.py`). Two options; the plan implementer picks one and states it:

- **Option A (preferred — real ORM):** add `pytest-django` to dev deps, a minimal `DJANGO_SETTINGS_MODULE` + test-DB config (sqlite in-memory is fine), and a new `tests/core/test_repositories.py` marked `@pytest.mark.django_db`. Because the repo method is `@sync_to_async`, either call its `.__wrapped__` synchronously under the marker or `await` it inside an async test with the async DB support. Assert: (a) expired active row → `is_active=False`; (b) row with `end_date == reference_date` is **not** touched (strict `<`); (c) `user_id` scoping deactivates only the target user; (d) an expired `is_default=True` row has **both** flags cleared; (e) already-inactive rows untouched and excluded from the returned count. This is the first ORM-backed test in the suite — treat harness setup as part of the task, not an afterthought.
- **Option B (no new infra):** keep it mock-based but assert the **query construction**, not just the service call — spy on `ExerciseChallenge.objects.filter` and the resulting queryset's `.update`, asserting the filter kwargs (`is_active=True`, `end_date__lt=reference_date`, and `user_id=` when scoped) and `update(is_active=False, is_default=False)`. Weaker than Option A (does not exercise real SQL) but implementable within the current harness; call out that the `is_default` interaction is only verified structurally.

## `RULES.md`

Add a subsection (e.g. under challenge / workout flow docs):

- **"Active for Telegram"** means in the date window: `is_active=True` AND `start_date ≤ today ≤ end_date` (`get_current_active` / `list_current_active_challenges`).
- When the in-window set is empty, workout parse/log flows must **not** fall back to all exercise types or invent `Day 1/30 · 990` cards.
- Expired challenges (`end_date < today`) are lazily deactivated (`is_active=False`, `is_default` cleared) via `list_current_active_challenges` and the evening reminder sweep.
