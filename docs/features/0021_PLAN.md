# Feature 0021 — Optional workout log motivational messages

GitHub issue #28: After logging a workout in Telegram, the bot appends an LLM-generated motivational/witty message to the response. Make this optional via a per-user setting — disableable while keeping normal workout stats/progress responses. This applies only to the immediate post-log Telegram reply, **not** evening reminder messages (`generate_reminder_motivation()`).

## Current behavior

In `app/services/workout_service.py` → `process_incoming_message()` (~L1217–1346):

1. For each parsed entry with an active challenge, calls `generate_motivational_response()` (`app/services/openai_service.py` ~L362–403) and appends the result to `witty_comments`.
2. After assembling stats/progress lines into `full_response`, appends `witty_comments[-1]` wrapped in `<i>…</i>` when the list is non-empty.
3. `generate_motivational_response()` calls the LLM; on failure it returns hardcoded fallback text `"Keep crushing it! 💪"`.

Reminder motivation is separate: `compute_evening_reminder()` (~L1422) calls `generate_reminder_motivation()` (~L1524); `send_evening_reminder()` (~L1555) consumes it. Both are **out of scope** for this feature.

## Workout logging — gate motivational comment

### `app/services/workout_service.py` — `process_incoming_message()`

**Load setting once per message** (~L760–762, where `update_chat_id` already runs):

1. Capture the return value: `user_settings = await user_settings_repo.update_chat_id(user.id, chat_id)` (method already returns `UserSettings`).

**Gate witty comment generation** (~L1285–1296):

2. Replace the unconditional `if challenge:` block with:

```
if challenge and user_settings.is_workout_motivation_active:
    comment = generate_motivational_response(...)
    witty_comments.append(comment)
```

When disabled:

- Do **not** call `generate_motivational_response()` (no LLM call, no fallback string).
- `witty_comments` stays empty → existing assembly at ~L1345–1346 skips the `<i>…</i>` append.
- Stats/progress lines, day-complete banner, habit-reward side effects remain unchanged.

**Do not** change `generate_reminder_motivation()` usage in `send_evening_reminder()` or any reminder idempotency paths.

### `app/services/openai_service.py`

No changes required for the must-have toggle. `generate_motivational_response()` stays as-is for enabled users. Future tone/template customization could add parameters or read from `UserSettings` later without changing the boolean contract.

### `tests/api/test_users.py`

- Update `test_get_current_user_profile`: add `is_workout_motivation_active=True` to the `mock_settings` `SimpleNamespace` (required once `UserSettingsOut` gains the field — `model_validate` will fail without it); optionally assert `payload["settings"]["is_workout_motivation_active"]` in the response.
- **Required** (not "if present"): add a `PATCH /api/v1/users/me/settings` round-trip test that sends `{"is_workout_motivation_active": false}` and asserts the value reaches `user_settings_repo.update()` (or the returned settings) and is echoed in `UserSettingsOut`. This is the documented per-user toggle surface (RULES.md: per-user settings managed via `PATCH /api/v1/users/me/settings`); without this test, forgetting to add the field to `UserSettingsUpdate` would be silently uncaught (`model_dump(exclude_unset=True)` drops unknown/absent fields, and no existing test exercises this write path).

### Workout log response behavior — new or extended module

Add focused tests (e.g. extend `tests/services/test_workout_empty_challenges.py` or new `tests/services/test_workout_motivation_setting.py`) that exercise `process_incoming_message()` with an in-window challenge and a successful parse:

| `is_workout_motivation_active` | `generate_motivational_response` | Sent Telegram text |
|---|---|---|
| `True` (default) | called once | contains stats line **and** motivational `<i>…</i>` suffix |
| `False` | **not** called | contains stats line; **no** `<i>…</i>` motivational line; no fallback `"Keep crushing it!"` |

Test setup pattern: reuse `_base_patches()` from `test_workout_empty_challenges.py`; mock `user_settings_repo.update_chat_id` to return a `SimpleNamespace`/`UserSettingsModel` with the desired flag; patch `generate_motivational_response` with a distinctive return value (e.g. `"MOTIVATION_MARKER"`) and assert presence/absence in `send_telegram_message` call args.

**Caution on `_base_patches()`**: it currently stubs `user_settings_repo.update_chat_id` as a bare async mock with no explicit return value. Once the gate reads `user_settings.is_workout_motivation_active`, a bare mock returns a `Mock` whose attribute is truthy — the enabled path would run "by accident" rather than via a real default-enabled setting. Every test touching the motivation gate (including the enabled/default case) MUST set `update_chat_id`'s return to a stub object with an explicit `is_workout_motivation_active` value, so the assertion pins actual behavior, not a truthy `Mock`.

Do **not** add tests asserting reminder behavior changed — reminders should remain independent.

## Out of scope

- Wiring `is_workout_motivation_active` to `generate_reminder_motivation()` / evening reminders.
- Tone/template customization (future `CharField` or enum on `UserSettings` can build on the boolean).
- Telegram bot command or inline UI to toggle the setting (API-only unless a separate issue adds bot UX).
- Changes to `generate_motivational_response()` prompt or fallback text.
