# 0018 — Challenge Exception Days

## Context

Allow a challenge to declare **exception days** — days that don't count toward the daily-target schedule (e.g. weekends). On an exception day:

- The user **may still log** workouts.
- Logged reps **still add to `cumulative_total`** (banked progress).
- The day is **not** counted in `total_days`, **not** counted in `day_number`, and the daily target on that day is treated as 0.
- `target_total` shrinks: `daily_target × (calendar_days − exception_days_in_range)`.

Two ways to declare exceptions, both per-challenge:

1. **Recurring weekdays** — e.g. "every Sat + Sun", stored on the challenge row as a CSV of **ISO weekday ints** (`1=Mon … 7=Sun`). ISO is the public API convention; comparisons use `date.isoweekday()`.
2. **One-off dates** — e.g. `2026-04-20`, stored as rows in a child table.

Both can coexist; the effective exception set is the union, intersected with the challenge's `[start_date, end_date]` window.

Configuration UX: extend the existing Telegram `/challenge` natural-language flow **and** add a new Telegram `/exception` command for managing exceptions on existing challenges. REST endpoints back both.

## Phase 2A — Stats Math, Logging, and REST API

### 2A.1 Stats computation

**Edit:** `src/api/services.py` → `compute_exercise_stats` (line 560).

Algorithm changes inside the `if challenge:` branch (around lines 607–615):

1. Parse `exception_weekdays` from the challenge dict (CSV string → `set[int]`).
2. Fetch `exception_dates` for the challenge via `challenge_exception_day_repo.list_for_challenge(challenge_id, user_id)`, unless the caller supplied a prefetched date set on the challenge dict to avoid N+1 calls.
3. `exception_set = expand_exception_dates(start_date, end_date, weekdays, explicit_dates)`.
4. `calendar_total_days = (end_date - start_date).days + 1`
5. `effective_total_days = calendar_total_days - len(exception_set)` (may be `0`). Use this real scheduled-day count for exposed `effective_total_days` and `target_total`; if a helper needs a positive denominator, introduce a separate local guard such as `math_total_days = max(1, effective_total_days)` and do **not** let that synthetic value create target debt.
6. `effective_day_number`: count of non-exception days `d` with `start_date <= d <= min(today_local, end_date)` and `d not in exception_set`. It can be `0` when today is before the first scheduled day or the whole window is exceptions. Clamp only the upper bound to `effective_total_days` for historical snapshots. If `today_local` itself is an exception day, `effective_day_number` is **frozen** at the count of non-exception days strictly elapsed before today (i.e. the previous workout day's number) — see "Today exception" example below.

   ```
   Mon=1, Tue=2, Wed=3, Thu=4, Fri=5
   Sat (today, exception): day_number=5  ← frozen
   Sun (today, exception): day_number=5  ← still frozen
   Mon next: day_number=6
   ```
7. Replace `total_days` and `day_number` used for status / target / expected math with `effective_total_days` and `effective_day_number`.
8. `target_total = daily_target * effective_total_days` (still computed, not stored; can be `0` only for an all-exception schedule).
9. Add a new computed flag `is_today_exception: bool` to `ExerciseStatsOut`. When `True`, the Telegram stats card **hides the daily ring entirely** and renders only the cumulative ring plus a "🏖️ Rest day — banked X reps today" badge. The daily-target line is omitted.
10. `cumulative_total` is unchanged: it still sums **all** logs in the challenge window via `log_repo.get_cumulative_count`. Banked exception-day reps inflate `cumulative_total` and therefore can flip status to `ahead`.

**Edit:** `src/api/models.py` → `ExerciseStatsOut`: add field

- `parse_exception_prompt` is **additive** by default (add to existing exceptions). It returns the *new* dates/weekdays the user mentioned, not the desired final state. - If the LLM returns dates outside the challenge window, surface a friendly error before any mutation.
- Before calling the LLM, support a deterministic fast path for common inputs (`weekends`, `weekdays`, ISO date lists, and `every <weekday>`). If the LLM cannot parse, fall back to a usage hint listing those strict tokens.

**Confirmation flow (mirrors `/challenge`)**: every `/exception add` mutation goes through a two-step confirm-then-apply flow. The handler:
1. Calls `parse_exception_prompt`, computes the resolved set of new dates and weekday additions, intersected with the challenge window.
2. Extends the same in-memory pending-state module used by `/challenge` with a flow `kind` / payload union so challenge creation and exception updates cannot collide. 3. Sends a preview message with an inline keyboard:

   • Sat Apr 18, Sat Apr 25 (recurring: weekends)

The handler resolves which challenge to mutate using the user's `is_default=True` challenge (mirrors how `/log` without an exercise type works). If no default challenge is set, reply with a clear error pointing the user at `/challenge` and `/setdefault` (or whatever the existing equivalent is — verify during implementation). Do **not** introduce a disambiguation keyboard for this version.

All mutations should call the new service functions directly rather than making HTTP self-calls, matching how other Telegram handlers reach into `src/api/services.py`.

After every successful mutation, re-render and send the same exception-days summary block as 2B.2.

## Edge Cases & Notes

- **All days are exceptions**: keep the real scheduled-day count at `0`, avoid divide-by-zero locally, and log a warning. The challenge becomes "log freely; no daily-target debt"; do not use a synthetic `1` effective day to compute `target_total`.
- **Leading exception days**: if a challenge starts on a rest day, `effective_day_number` is `0` until the first scheduled day. This prevents a weekend-start challenge from being behind before Monday.
- **Exception date outside challenge window**: silently ignore in the math but reject at API boundary with 422.
- **Banked reps and `ahead` status**: with the user's chosen semantics, logging on weekends will push status to `ahead` once cumulative exceeds `daily_target × effective_day_number + threshold`. This is intentional and matches the "Yes — logs count, day doesn't" decision.
- **Historical log snapshots**: existing logs created before this feature have `status` / `day_number` snapshots based on the old math. We do **not** backfill — those snapshots remain accurate as of the time they were written. Live `compute_exercise_stats` calls use the new math.
- **Removing an exception date with existing logs**: logs stay attached and untouched. The next `compute_exercise_stats` call automatically reflows the math — that date now contributes to `effective_total_days` and its reps now count toward the daily-target check for that day. We do **not** rewrite log row snapshots when an exception date is removed; the snapshot is a historical record of what the user saw at log time.
- **Daily-target on an exception day**: if today is in `exception_set`, `compute_exercise_stats` should report `is_daily_complete=True`, `catch_up_reps=0`, and `is_today_exception=True`. The Telegram stats card hides the daily ring entirely on these days; only the cumulative ring + "🏖️ Rest day — banked X reps today" badge is shown. The frozen `day_number` (= count of non-exception days strictly before today) is used for the cumulative status.
- **Challenge `total_days` field on `ExerciseChallengeOut`** (line 89): keep this as the *calendar* total for backwards compatibility; expose the new `effective_total_days` separately.
- **Date range updates**: if `start_date` / `end_date` changes without replacing `exception_dates`, keep stored rows but hydrate and compute only the rows inside the current challenge window. This matches the "effective set is intersected with the window" rule.
- **No default exceptions**: `/challenge` does **not** auto-mark weekends. Exceptions are only set if the user explicitly mentions them ("every weekday", "except weekends", "skip Sundays") and the LLM extracts them. A bare "30 pushups per day for 30 days" creates a challenge with zero exceptions, identical to today's behavior.
- **List rendering**: `/exception list` and the challenge stats card render every exception date in full, with no truncation or grouping. Acceptable even for ~26 weekend dates in a 90-day challenge.
- **No forward-looking 'next rest day' hint** in stats cards or `/exception list` — keep these views minimal.
